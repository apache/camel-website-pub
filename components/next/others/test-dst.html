Test DST

Since Camel 4.24

The camel-test-dst module runs the real code of a Camel consumer under a deterministic, seeded, virtual-time scheduler. Only the external system is faked. A test runs thousands of seeds in seconds, and a failing seed replays with the same step trace.

  • Every thread pool created through the ExecutorServiceManager is backed by one event loop on the test thread (DstThreadPoolFactory). Tasks run one at a time; when several can run, the seed picks one.

  • Time is virtual: it jumps to the next due task. The time reads, sleeps and blocking waits of the code under test are rewritten at test time (@DstInstrument), so "wait 30 seconds" costs nothing.

  • A fake of the external system (a queue, a checkpoint store, a web API) injects faults chosen by the same seed.

  • Invariants are checked at the end of each run.

  • @DstTest(seeds = 1000) runs a test method once per seed. A failing seed is printed with its trace and is replayed exactly with -Ddst.seed=4711 or @DstSeed(4711).

This is a test tool. Nothing of it runs in production, and it changes nothing in Camel.

A test

@DstInstrument("org.apache.camel.component.aws2.sqs")
class SqsVisibilityDstTest {

    @DstTest(seeds = 1000)
    void noMessageIsDeliveredAgainWhileTheConsumerHoldsIt(Dst dst) throws Exception {
        new SqsWorld(dst).run();
    }
}

The world (SqsWorld) builds a CamelContext with DstCamel.newContext(dst), binds the fake client, starts the route, drives the run with dst.runUntil(…​) and dst.runFor(…​), and checks the invariants with dst.check(…​). The test and its world live in a package of their own (for example org.apache.camel.component.aws2.sqs.dst); that package is never rewritten.

A Dst is one run. The extension creates one per seed and closes it after the seed; a test that creates its own new Dst(seed) closes it in a finally. The virtual clock is JVM-wide, so only one run may be open at a time: a second new Dst while another run is open throws IllegalStateException ("another run (seed N) is still active"), and a DST test refuses to start when JUnit runs tests in parallel (junit.jupiter.execution.parallel.enabled=true).

What the harness controls

Thread pools

Every pool and scheduled executor created by Camel or the component through the ExecutorServiceManager. A single-thread executor keeps its FIFO order; an executor with n threads offers its first n runnable tasks to the seed.

Time reads

System.currentTimeMillis(), System.nanoTime(), new Date(), Instant.now(), Clock.systemUTC(), Clock.systemDefaultZone(), Clock.system(ZoneId) and now() / now(ZoneId) of LocalDateTime, ZonedDateTime, OffsetDateTime, LocalDate, LocalTime and OffsetTime, in the packages of @DstInstrument.

Sleeps

Thread.sleep and TimeUnit.sleep: on the loop thread a sleep is a virtual wait. The sleeping task keeps its thread and the other tasks run meanwhile.

Blocking waits

CompletableFuture.get/join, Future.get, CountDownLatch.await, Semaphore.acquire/tryAcquire, DelayQueue and BlockingQueue take/poll: the loop runs until the wait can end, and a timed wait gives up in virtual time. A wait that no task of the run can end fails the seed at once and names the call site.

Timed waits on tasks

Future.get(timeout) on a task of the run and awaitTermination time out in virtual time.

Parallel streams

parallelStream() of a java.util collection is rewritten to stream(): the elements are handled in order by the calling task, not on the common fork-join pool.

@DstInstrument(alsoRewrite = …​) applies the same rewriting to classes outside the code under test, for example org.apache.camel.util.StopWatch, org.apache.camel.support.MonotonicClock, org.apache.camel.support.task (ForegroundTask), org.apache.camel.processor.errorhandler (synchronous redelivery) or org.apache.camel.impl.engine.DefaultShutdownStrategy (its wait for in-flight exchanges). This is a stop-gap: Camel core reads System directly, and a time source in core that the harness can replace needs a dev@ discussion first.

Escapes and strict mode

Before the first seed, the harness scans the packages under test and writes every escape point to target/dst/<Test>.escapes.txt: own threads and executors, the common fork-join pool, Reactor schedulers, waits it cannot run the loop for (Object.wait, LockSupport.park, Mono.block), wall clock reads it does not rewrite.

Strict mode is the default: when a seed reaches one of these at runtime, or a thread outside the harness submits a task to the loop, reads the virtual clock or sleeps, the seed fails with the escape as its cause. A clock read from such a thread (a Reactor or Netty thread, for example) still gets the virtual time and its sleep still takes real time, so that thread mixes the two; this is what strict mode is there to make visible. @DstInstrument(allowEscapes = "Foo.bar") allows an escape that cannot change the result (say why in a comment); @DstInstrument(strict = false) or -Ddst.strict=false only records escapes in target/dst/<Test>.summary.txt.

A wait in code that is not rewritten (a latch in Camel core, for example) blocks the loop thread for real. A watchdog interrupts the loop thread after 10 s of real time without progress (-Ddst.watchdogMillis) and the seed fails with the stack where it was blocked.

The one-stack model

All tasks run on one thread, the test thread. A task that blocks (a call of the fake with a latency, a sleep, a wait) stays on the stack while the loop runs the other tasks nested above it. So a blocked task can resume only after every task that blocked after it has resumed. Three consequences:

  • Timing: see the rule in the guide below.

  • A timed wait notices its timeout only when the tasks nested above it return. If the awaited task completes after the deadline that way, the caller still gets the TimeoutException, but the task’s side effects have already happened.

  • A route stop or suspend that runs while an exchange is blocked in a synchronous call below it on the stack cannot see that exchange finish. The Slack world therefore copies the suspend sequence of DefaultShutdownStrategy with a short polling wait instead of calling suspendRoute. With an asynchronous downstream call (DstCamel.asyncStep) a real stopRoute works.

Code that uses its own threads or a third-party scheduler (the Azure SDKs on Reactor) is outside the harness; fake the client at a level above those threads.

Writing a fake world: a guide for AI agents and humans

A world is the component’s real consumer, a fake of the external system, a load (producers, operators), seeded faults and invariants. This guide uses the SQS world of camel-aws2-sqs (FakeSqs, SqsWorld, about 420 lines) as the worked example. Follow the steps in order.

1. Find where the client is swapped

Look for the place where the component gets its client:

  • an endpoint option that takes a client instance, bound in the registry. camel-aws2-sqs has amazonSQSClient:

    context.getRegistry().bind("sqs", fakeSqs);   // FakeSqs implements SqsClient
from("aws2-sqs://dst?amazonSQSClient=#sqs&queueUrl=RAW(" + FakeSqs.QUEUE_URL + ")&extendMessageVisibility=true"
     + "&visibilityTimeout=" + visibilityTimeout + "&maxMessagesPerPoll=" + maxMessagesPerPoll
     + "&concurrentConsumers=" + concurrentConsumers + "&initialDelay=100&delay=" + delay)

  • else a static factory, replaced with Mockito’s mockStatic for the duration of the run (the Event Hubs world mocks EventHubsClientFactory, the Slack world mocks Slack.getInstance).

Fake the client at the level where the component calls it synchronously. If the client runs its own threads (Reactor, Netty, an HTTP client pool), fake it above them.

2. Run the escape scan before writing anything

Write the smallest test with @DstInstrument("<component package>") and one seed, run it, and read target/dst/<Test>.escapes.txt. Every line is a place where the component leaves the harness. For each one, decide:

  • fix it in the harness (the time reads, sleeps and waits listed above are already handled),

  • avoid it with the configuration of the world (the first SQS world kept maxMessagesPerPoll at 10 or less because more joined several requests with CompletableFuture.get(); the harness now runs the loop for that wait), or

  • document it, in the world’s Javadoc, and allow it in strict mode only if it cannot change the result.

The SQS scan flagged Instant.now() in the visibility extender. Before it was rewritten, 271 of 500 seeds on main failed falsely: the extender computed its deadline from real time while the fake counted in virtual time.

3. Write the fake from the service’s documentation

Write the fake from the API reference of the service, not from the component’s code: a fake copied from the consumer agrees with the consumer’s bugs. Quote the rule next to the code that implements it, name the page, and mark what is assumed:

// [R] "Valid values: 1 to 10. Default: 1." and "Amazon SQS never returns more messages than this value
// (however, fewer messages might be returned)"
int max = request.maxNumberOfMessages() != null ? request.maxNumberOfMessages() : 1;
...
// [D] "If you use an old ReceiptHandle, the request will succeed, but the message might not be deleted."
if (dst.chance(0.5)) {
    delete(m, "deleted (old handle)");
}
...
// [C] "ReceiptHandleIsInvalid: The specified receipt handle isn't valid." (assumed for a deleted
// message and for the handle of an earlier receive; the page does not spell these cases out)

Where the documentation allows several behaviours ("might", "fewer messages might be returned"), let the seed choose. List what is not modelled in the class Javadoc (FakeSqs: long polling, FIFO queues, the in-flight limit, retention, dead-letter queues).

4. The one-stack timing rule

A blocked task resumes only after the tasks that blocked after it. A call of the fake that blocks for its latency can therefore return later than its latency, and anything it decides at the start can be stale at the end. The rule:

  • reads take effect at the end of their latency: FakeSqs.receiveMessage blocks first, then picks the visible messages and starts their visibility timeout;

  • writes take effect at the start: deleteMessage deletes, then blocks for its latency;

  • background tasks do not block: the visibility extender of the consumer runs on a scheduled executor, so changeMessageVisibilityBatch answers without a latency. If it blocked, a delayed resume could make the extension arrive after the timeout it extends, which is not what SQS does.

Write this down in the fake’s Javadoc, as FakeSqs does.

5. Let the seed pick the configuration

The seed picks the endpoint configuration as well as the timing, at the start of the run, and the world writes it to the trace:

this.visibilityTimeout = dst.pick(List.of(2, 3, 5, 10));
this.maxMessagesPerPoll = dst.pick(List.of(1, 2, 5, 10));
this.concurrentConsumers = dst.pick(List.of(1, 2, 3));
this.delay = dst.pick(List.of(100L, 500L, 1000L));
dst.trace("world: visibilityTimeout=" + visibilityTimeout + " maxMessagesPerPoll=" + maxMessagesPerPoll + ...);

This found CAMEL-25737: with visibilityTimeout=1 the extender is always late. It is left out of the default set while that issue is open, and -Ddst.sqs.visibilityTimeouts=1 puts it back. The seed of a run is scrambled (SplitMix64), so consecutive seeds draw unrelated configurations.

6. Seeded faults, a drain phase, and fault-excuse records

Inject the faults the service documents (failed calls, slow answers, lost requests) with dst.chance(…​), at a rate that still lets work get done (the SQS world: 5 % failed receives and deletes, 2 % failed visibility changes, 15 % slow processing). Then switch the faults off and let the system drain:

dst.runUntil(() -> sendsLeft == 0, "all sends");
dst.runFor(dst.between(0, 3L * visibilityTimeout * 1000));
// faults cleared: the queue must drain
faults = false;
sqs.faults = false;
// drain while it makes progress: stop when no message was deleted for a while, or at a cap
long quiet = 20L * visibilityTimeout * 1000 + 30_000;
long cap = dst.now() + 3_600_000;
int left = sqs.notDeleted().size();
long lastProgress = dst.now();
while (!sqs.allDeleted() && dst.now() < cap && dst.now() - lastProgress < quiet) {
    dst.runFor(100);
    int remaining = sqs.notDeleted().size();
    if (remaining < left) {
        left = remaining;
        lastProgress = dst.now();
    }
}

Drain until progress stops, not for a fixed time. With a fixed drain time, 1 of 20,000 seeds failed falsely: one consumer taking one message per poll was still deleting messages when the time ran out.

Some faults legitimately cause what the invariant forbids. Record which fault excuses which violation, and only those: a failed ChangeMessageVisibilityBatch lets SQS deliver the messages of that batch again, so FakeSqs reports their ids (onExtensionFault) and the world does not count a redelivery of those messages.

7. The invariant comes from the component’s contract

Write the property the component promises, not what the code happens to do. The visibility extender promises that a message is not delivered again while the consumer holds it. The world records what happened in a DstLedger and checks:

dst.check(
        Invariants.of("no message is delivered again while the consumer holds it",
                () -> redeliveredWhileHeld.isEmpty() ? null : redeliveredWhileHeld.toString()),
        Invariants.everyOfferedRoutedAtLeastOnce(ledger, "sent", "completed"),
        Invariants.of("the queue is drained once the faults cleared",
                () -> sqs.allDeleted() ? null : "not deleted: " + sqs.notDeleted()));

Start from the reusable Invariants (everyOfferedRoutedAtLeastOnce, noDuplicates, lastCompletedAcknowledgedWhenQuiet, acknowledgedWithin, routeStarted) and add the component’s own with Invariants.of(name, check). A violation message carries the configuration, so the failure report is readable on its own.

8. The self-check

A world is only evidence when it can fail. Before trusting a pass on main:

  1. Fail on the code before a past fix. Find a fixed bug of the same behaviour with git log on the component (the SQS world: CAMEL-25700, commit d09593b4a584). Revert the fix locally and run the world: it must fail (1397 of 5000 seeds), and only in the configurations the fix describes (for CAMEL-25700: maxMessagesPerPoll >= 2 and concurrentConsumers >= 2).

  2. Pass on main, with thousands of seeds (-Ddst.seeds=5000).

  3. Replay: run a failing seed twice with -Ddst.seed=<seed>. The trace files in target/dst/ must have the same SHA-256 (it is on their second line).

If the world cannot fail on the old code, its fake, its load or its invariant is too weak.

9. Triage before reporting

A failing seed is not yet a bug. Before reporting one:

  1. Group the failing seeds by configuration (the world: line of each trace, or the violation message). A failure that appears only in one configuration points at that configuration (CAMEL-25737 was all visibilityTimeout=1).

  2. Read one trace from the start: what the world chose, then each step with its virtual time and executor.

  3. Tell three causes apart:

    • a harness artifact: an escape (check the summary), the one-stack rule broken by the fake, a time read that is not rewritten (before the Instant.now() rewrite, half of the SQS seeds failed this way);

    • a fake mistake: the fake does something the service documentation does not allow;

    • a real bug: the consumer breaks its contract against a fake that follows the documentation.

  4. Reproduce a real bug outside DST too, with a plain unit test, before filing it.

Pitfalls seen when agents wrote worlds

Agents wrote nine worlds with this guide. These mistakes came up:

  • Timestamps at 0. Give the times of the fake virtual wall clock time (Dst.EPOCH_MILLIS + dst.now(), or dst.currentTimeMillis()), not 0. A Service Bus fake with lock times in 1970 made the lock renewer renew on every run, so the world could not fail. The self-check (fail on the code before the fix) caught it.

  • No end to the run. A consumer that loops forever needs an unwind at the end of the run, or the run never ends: cancel its task through the task registry, or stop the route at the end of the drain phase. A consumer task that never returns (a pull loop) sits above the test thread on the one stack, so a dst.runFor or dst.runUntil in the test body does not return while it loops, and the seed fails on the step budget. Make the phases of the run (clear the faults, drain, end) scheduled tasks, and end the run by having the fake end the loop (close the subscription), then dst.runUntil(() → closed, "subscription closed").

  • A fake that blocks under a lock. A call of the fake made while the consumer holds a lock must not block: with the one-stack rule, the tasks nested above it run while the lock is held.

  • A violation without its excuse. Every invariant needs the record of which injected faults excuse a violation of it. Without it, a message dead-lettered after injected acknowledgement faults showed up as a false failure.

  • Old traces. Clear target/dst between runs, or the traces of an earlier run end up in the grouping of the failing seeds.

  • A loud test log. A consumer looping under a buggy fake wrote a 31 GB test log and filled the disk. Set the component to WARN in the test log4j2 configuration, or cap the log.

  • A fixed configuration. Let the seed pick the endpoint configuration, edge values included. That is how CAMEL-25737 (visibilityTimeout=1) and CAMEL-25741 (aws2-ddbstream, found with a fake DynamoDB Streams world) were found.

Later worlds (IMAP, JMS, NATS JetStream, Azure Service Bus) showed more:

  • An empty answer at once. A fake that answers at once with nothing (no message, no responder) lets a consumer with its own receive loop (JMS, a NATS fetch) spin without virtual time moving; the seed fails on the step budget or the watchdog instead of reaching its end. Give every call of the fake a round-trip latency.

  • A proxy that throws what the interface does not declare. A java.lang.reflect.Proxy keeps the fake of a wide interface (JMS) small. A checked exception that the interface method does not declare comes out of the proxy as UndeclaredThrowableException; do what the library does instead (for an InterruptedException in a fetch: set the interrupt flag again and return).

  • Only the protocol. Model what the client library does with the objects of an earlier connection, not only what the server does: after a reconnect, a message or handle from before may still work, fail, or now refer to something else. Read the library (its source, or its byte code) for that.

  • One excuse for every stop. Each kind of operator stop needs its own excuse record: a consumer stopped through JMX and a route stop that hits the shutdown timeout leave different work unfinished (a lock renewer cancelled under exchanges still in flight, for example).

  • A synchronous consumer over an asynchronous step. With DstCamel.asyncStep in the route, a consumer that calls the route synchronously waits on a latch of org.apache.camel.impl.engine.DefaultAsyncProcessorAwaitManager: add it to alsoRewrite, or the watchdog fails the seed. Let the asynchronous exchanges in flight finish before dst.dropPending(), which drops their answers too, so that the shutdown does not wait for exchanges that cannot complete.

Checklist

  • The client is swapped through an endpoint option or a static mock, at a synchronous level.

  • The escape scan was read; every escape is fixed, avoided or documented; the test runs in strict mode.

  • Every behaviour of the fake quotes the documentation; assumptions are marked; what is not modelled is listed.

  • Reads take effect at the end of their latency, writes at the start; background tasks do not block.

  • The seed picks the configuration, edge values included, and the world traces it.

  • The fake’s timestamps are virtual wall clock time (Dst.EPOCH_MILLIS based), not 0.

  • A consumer that loops forever is unwound at the end of the run.

  • Faults are seeded, switched off for a drain phase, and recorded where they excuse a violation.

  • The component logs at WARN in the test log configuration, and target/dst is cleared between runs.

  • The invariant states the component’s contract.

  • The world fails on the code before a past fix, passes on main, and a seed replays with the same SHA-256.

Running the tests

The worlds are tests of their components, in a dst package. Build the harness in the same reactor as the component (-pl both), so that the component’s tests see it. -Dsurefire.rerunFailingTestsCount=0 stops surefire from running each failing seed again. A component whose tests depend on a camel-test-infra-* module (camel-nats, camel-azure-storage-queue) needs that module in -pl too when it is not in the local repository.

DST=components/camel-test/camel-test-dst
SQS=components/camel-aws/camel-aws2-sqs
EH=components/camel-azure/camel-azure-eventhubs
SLACK=components/camel-slack
MVN="./mvnw -B -Papache-snapshots test -Dsurefire.failIfNoSpecifiedTests=false -Dsurefire.rerunFailingTestsCount=0"

# the harness self-tests
$MVN -pl $DST -Dtest='Dst*Test'

# the worlds, 1000 seeds each, then 5000 seeds without stopping at the first failing one
$MVN -pl $DST,$SQS,$EH,$SLACK -Dtest='*DstTest'
$MVN -pl $DST,$SQS,$EH,$SLACK -Dtest='*DstTest' -Ddst.seeds=5000 -Ddst.maxFailures=100000

# the self-check: revert the main code of a past fix locally (do not commit), run the world, restore
git show d09593b4a584 -- $SQS/src/main | git apply -R          # CAMEL-25700
$MVN -pl $DST,$SQS -Dtest=SqsVisibilityDstTest -Ddst.seeds=5000 -Ddst.maxFailures=100000
git checkout -- $SQS/src/main

# replay one seed twice and compare the traces
$MVN -pl $DST,$SQS -Dtest=SqsVisibilityDstTest -Ddst.seed=8
cp $SQS/target/dst/SqsVisibilityDstTest.*/seed-8.trace /tmp/seed-8.first
$MVN -pl $DST,$SQS -Dtest=SqsVisibilityDstTest -Ddst.seed=8
diff /tmp/seed-8.first $SQS/target/dst/SqsVisibilityDstTest.*/seed-8.trace && echo identical

The past fixes of the other two worlds are 83aaa80754f9 (CAMEL-25683, Event Hubs) and 68329f0919bc (CAMEL-25684, Slack). Two system properties belong to a world rather than to the harness: dst.sqs.visibilityTimeouts (the visibility timeouts the SQS world picks from, default 2,3,5,10; 1 shows CAMEL-25737) and dst.replayCheckSeed (the seed of the in-JVM replay test of the Event Hubs world, default 1).

Limits

  • Interleaving is per task: the harness does not preempt a task in the middle of a method.

  • The one-stack model above: a blocked task resumes only after the tasks that blocked after it.

  • Code on its own threads or on a third-party scheduler is outside the harness; strict mode makes reaching it fail the seed.

  • One run per JVM at a time: the active run, and so the virtual clock, is a static field, and every rewritten clock read in the JVM sees it. A world must therefore not go into a module that runs its tests in parallel (camel.surefire.parallel=true, as camel-jms and camel-sql do): the other tests in that surefire fork would read the virtual clock while a run is active. The harness enforces this: a second run while one is open fails, and a DST test refuses to start when JUnit runs tests in parallel. A local world in such a module (camel-sjms, for example) can still be run alone, with -Dtest=<the world> -Dcamel.surefire.parallel=false, but it cannot be committed there: the module’s own build would fail it.

  • Locks do not exclude: every task runs on the test thread, so a ReentrantLock or synchronized block held by a blocked task is entered again by the tasks nested above it. A critical section is atomic only because the fake does not block inside it, and races between two code paths that each hold a lock cannot be explored.

  • The rewriting stays for the rest of the surefire fork: the classes of the @DstInstrument packages (the component’s main classes, and its test classes in the same package) stay rewritten for every test that runs after the DST test, the same as the alsoRewrite entries. Outside a run they read the real clock and sleep for real, so the other tests of the component still pass.

  • The results are only as good as the fake of the external system.
